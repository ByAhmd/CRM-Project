# Permission model

Decisions D-3, D-4, D-13, D-14, D-15, D-16, D-17, D-18, D-19, D-20, D-21, D-22, D-23, D-25 and A-12 as implemented in the foundation.

## Where authority lives

| Layer | Class | Answers |
|---|---|---|
| Permission catalogue | `App\Enums\Permission` | Every key the code checks (`lead.view_any`, `deal.change_stage`, `settings.manage`, …). The seeder creates a row per case and prunes stale rows. |
| Default roles | `App\Support\Access\RolePermissionMatrix` + `Database\Seeders\RolesAndPermissionsSeeder` | What a fresh install grants each of the seven seeded roles. Editable roles are **not** reset by re-seeding; `super_admin` is always re-granted everything. A seeded role added later (`employee`, D-15) is created with its defaults by the next `db:seed` on an existing install; a hand-made role that already used the `employee` key is first moved to `employee_legacy` (users, permissions and names kept) by the migration the deploy runs before seeding. |
| Runtime authority | spatie `roles` / `permissions` tables, edited through the **Roles** resource (`roles.manage`, super admins only) | What a role may do right now. Every change is written to the audit ledger by `App\Services\Access\RoleService`. |
| Record scope | `App\Services\Access\RecordVisibilityResolver` | Which records of an owned entity a user reaches: own (`*.view_any`), team (`*.view_team`), all (`*.view_all`). |
| Enforcement | `App\Policies\*` (owned entities use `Policies\Concerns\ChecksPermissions`), Filament `can*` methods, `->authorize()` on actions, `->authorizeIndividualRecords()` on bulk actions, `ScopesQueriesToVisibleRecords` on resource queries | Both the permission and the scope must pass. |

## Seeded roles

| Role | Visibility | May do |
|---|---|---|
| `super_admin` | all | everything, including role administration (`roles.manage`, which also opens System → Backups and the backup downloads, D-16); locked (cannot be renamed, deleted or stripped) |
| `admin` | all | everything except `roles.manage` (including `account.set_type` and `activity.assign`); `users.manage` never reaches a super admin account |
| `sales_manager` | team | create, update, delete and restore leads/contacts/accounts/deals; create, update, delete and restore the team's tasks (there is no `task.restore` key: `TaskPolicy::restore()` is granted with `task.delete`, so the restore actions on the task pages and the table's restore bulk action are open to this role); log and delete activities (activities are immutable: no update); reassign leads, contacts, accounts, deals and activities (incl. `activity.assign`) but not tasks — task assignment is admin-only (D-14), so the manager works the team's tasks without handing them out; change lead status, convert, change stage, close, merge contacts and accounts, import and export the four commercial entities, export activities and tasks; notes, attachments (upload, download, delete); send email, read email templates and products, reports; holds `imports.view` / `exports.view`, which at team level opens only its own runs (see below); no settings, users, teams, roles or audit; may not set the account type by hand |
| `sales_rep` | own | create/update own leads/contacts/accounts/deals, change status/stage, convert, close, log activities (no delete), create, update, delete and restore own tasks (restore is granted with `task.delete`, `TaskPolicy::restore()`), create/update/delete notes, attachments (upload, download, delete), send email, read email templates and products, reports, export the four commercial entities plus activities and tasks **own scope only**; no reassign, no import, no merge, no delete or restore of commercial records (leads, contacts, accounts, deals), no import/export history of others; the account type follows the deals (no `account.set_type`) |
| `support` | all (read) | read leads, contacts, accounts, deals, activities and tasks at all level, email templates and products; log activities; create and update notes and tasks; upload (`attachment.create`) and download attachments; export leads/contacts/accounts/deals within scope (D-13); reports; no commercial writes, no deletes, no reassign, no import |
| `read_only` | all (read) | read leads, contacts, accounts, deals, activities and tasks at all level, email templates and products; download attachments; export leads/contacts/accounts/deals within scope (D-13); reports; writes no record — the one write it keeps is a **comment on a task** it can open (D-17: commenting follows `view`, and this role views every task at all level). Comments are immutable and notify the task's participants, so an auditor who must leave no trace at all needs a custom role without `task.view_any` |
| `employee` (D-15) | own (tasks only) | `workspace.tasks`, `task.view_any`, `task.create`, `task.update`, `task.delete` and `attachment.create`, `attachment.download` — nothing else. Lists, creates, updates, deletes and restores their own tasks (a task can only be created for oneself: no `task.assign`); enters the Tasks workspace only (`workspace.tasks`, D-23): the shared tasks board, the calendar and the Tasks home's two task lists; uploads and downloads files on the tasks they may open (the attachments panel on the task page — `AttachmentPolicy` follows the task's `view`, so no lead, contact, account or deal file is ever reached). A task handed to them is read-only apart from start / post update / tick its checklist / complete / reopen-from-completed (D-14 amendment, D-25). No leads, contacts, accounts, deals, activities, notes, email, products, email templates, reports, exports, imports, settings, users, teams, roles or audit — the Sales, Reports and Administration workspaces answer 403, record pages included; a linked record the employee cannot open is shown as plain text, never as a link |

## Workspaces (D-23)

The CRM is split into a home panel (`/app`: sign-in, password reset, profile and two-step verification, notification preferences, the workspace screen) and four workspace panels. Four keys, shown first in the Roles editor as «مساحات العمل», decide which workspaces a role may enter; inside a workspace every page keeps its own permission and record scope exactly as above. `App\Services\Access\PanelAccess` is the one rule (`User::canAccessPanel()` delegates to it): the home panel admits every active user; a workspace admits an active user holding its key; anything else is refused (fail closed). A refused workspace answers 403 — except the bare `/admin`, the pre-D-23 dashboard address, which sends a user without Administration to the workspace screen.

| Key | Workspace | Seeded roles holding it |
|---|---|---|
| `workspace.sales` | Sales `/sales` — leads, deals, deal board, contacts, accounts, products, activities, email templates, import and export history | super_admin, admin, sales_manager, sales_rep, support, read_only |
| `workspace.tasks` | Tasks `/tasks` — tasks, tasks board, routine tasks, calendar | all seven |
| `workspace.reports` | Reports `/reports` — the nine reports | super_admin, admin, sales_manager, sales_rep, support, read_only |
| `workspace.admin` | Administration `/admin` — users, roles, teams, general settings, lookups, pipelines, custom fields, lead-scoring rules, audit log, backups | super_admin, admin |

**Migration rule.** Existing roles were granted by the data migration `2026_10_05_100001_grant_workspace_permissions_to_existing_roles`, which runs before `db:seed` in a release: the seven seeded roles get the defaults above; a custom role gets a workspace when it already holds any key one of that workspace's pages needs — Sales for any `lead.*`, `contact.*`, `account.*`, `deal.*`, `activity.*`, `product.*`, `email_template.*` or `note.*` key, `email.send`, `imports.view`, `exports.view` or `task.export`; Tasks for any `task.*` key; Reports for `reports.view`; Administration only for an administration key (`users.manage`, `roles.manage`, `teams.manage`, `settings.manage`, `audit.view`). Attachment keys grant nothing on their own. Grants are only added, so a second run changes nothing; after the release the keys are edited like any other permission in the Roles editor (D-3: a redeploy never resets them).

**A workspace key opens the door, never a page.** A role holding `workspace.sales` but no `lead.view_any` enters Sales and sees no lead list (the page answers 403 like before D-23); a role holding `lead.view_any` but not `workspace.sales` sees the Sales card locked and is refused at `/sales`. Grant both.

**Link rules.** Resources and pages build their addresses in the workspace that registers them (`BuildsUrlsInOwningPanel`, `BuildsPageUrlsInOwningPanel`), wherever the link is built. A link into another workspace is shown only to a reader who may enter it (`PanelUrl::forReader()`, `RecordUrl::forReader()`): the bell notice and the mail keep their text but drop the *Open* button, the timeline, the calendar, the task page's linked record and the workspace homes show plain text. The workspace screen shows every card, the switcher only the enterable workspaces. After sign-in a user returns to the address they were following only when it lies inside a panel they may enter; otherwise they land on the workspace screen. Every pre-D-23 `/admin/...` address of a moved page answers 301 to its new address (query string kept), and the new address then applies the rules above.

## Guards above the permissions

- Nobody may delete, disable or set back to pending their own account (`RoleService::assertStatusChange`).
- The last active `super_admin` cannot be demoted, disabled, set to pending or deleted (`RoleService::isLastActiveSuperAdmin`).
- Only a `roles.manage` holder (a super admin) grants, removes or edits `super_admin`. `users.manage` never reaches a super admin account: update, status, invite, delete and restore are all refused (`UserPolicy`, `RoleService::syncUserRoles` / `assertStatusChange`, A-12).
- Pending is reached only through an invitation; the status field offers Active and Disabled, and Pending only while the account still is pending.
- Import/export history: a user always sees and downloads their own runs. `exports.view` / `imports.view` open another user's run only for entities the holder reaches at all level (`{entity}.view_all`). The rule is enforced on the history screens and on Filament's `/filament/exports/{export}/download` and `/filament/imports/{import}/failed-rows/download` routes (policies registered for Filament's base models too).
- An account that cannot sign in (disabled, pending) reaches no import/export run or file, even with a live session, and receives no notification on any channel.
- Event notifications go only to recipients who can open the record (`NotificationRecipients`). A team's manager is chosen among the team's active members.
- A lifecycle type is set by hand only with `account.set_type` (D-6); otherwise a prospect becomes a customer on its first won deal.
- A change of owner through any form, assign action or importer goes through `RecordAssignmentService` (`{entity}.assigned` audit event and a notification to the new owner); only active users who hold the entity's `{group}.view_any` (through a role or a direct grant) are assignable (`RecordVisibilityResolver::assignableUsers`), so a record is never handed to someone who cannot open it — an `employee` (D-15) can be given tasks, never a lead, contact, account, deal or activity. An import row that names a new owner for an existing record needs that record's `assign` verb, and the reassignment is written in the row's savepoint (`ResolvesImportLookups`). A new record created for another owner is a creation, not a reassignment — except that a task created for someone else also notifies its assignee (D-14: under admin-only task assignment, creating a task for an employee is how work is handed out); the ledger still records the creation.
- Task assignment is admin-only (D-14): `task.assign` is held by `super_admin` and `admin` alone. The verb still answers to record scope, so a role a super admin grants `task.assign` at team level assigns inside the team only. The shared tasks board (`TasksBoard`, `task.view_any`) shows every user's open tasks and assignees to every role (the employee included, D-15) — the one page-scoped exception to own/team visibility — but links a card to its task only where the viewer's `view` policy allows.
- A handed-out task belongs to its assigner (D-14 amendment, 2026-09-28). A task is *handed out* to a user when they are its assignee and `assigned_by` names someone else; for that user, unless they hold `task.assign`, `TaskPolicy::update` (the details: title, description, kind, priority, dates, reminder, related record, recurrence — the edit page, the edit actions and modals, the calendar move), `cancel`, `delete` and `restore` refuse. The rows above therefore read "update, cancel, delete and restore the tasks within scope *except those handed out to oneself*" for `sales_manager`, `sales_rep`, `support` and `employee`. The assignee reports on the work through `TaskPolicy::progress` — the former `update` rule, `task.update` plus record scope, never on a deleted task — which governs `start` (Pending → In progress), `postUpdate` (a progress note), `complete` and `reopen` of a *completed* task; a *cancelled* task reopens only under `update`. The assigner, administrators and any other holder of `task.update` within reach (a team manager) keep editing; a task a user created for themselves stays fully theirs; a task with no recorded assigner (created before `assigned_by` existed) is not handed out. Starts and updates notify the assigner (`NotificationEvent::TaskProgress`, bell by default, mail opt-in) under the completion notice's recipient rule.
- **Task checklists split like the task itself (D-25).** Writing the checklist — adding, renaming, reordering and removing items, in the task form — is `TaskPolicy::update`, so the handed-out assignee cannot change it while the assigner, administrators, a team manager within reach and the creator of their own task can. Ticking and unticking is `TaskPolicy::tickChecklist`: `progress` (`task.update` within reach — the handed-out assignee included) on an *open* task; a completed, cancelled or deleted task's checklist takes no ticks, and a mentioned participant (D-20), who holds no `progress`, never ticks. No new permission key. Ticks are audited on the task, never notified.
- Commenting on a task follows `view` (D-17, `TaskPolicy::comment`): every role that can open a task — `read_only` and the handed-out assignee included — may comment on it, never on a deleted task. There is no `task.comment` key; to keep a role from commenting, keep it from viewing tasks. Comments are text only, never edited or deleted, and notify the assignee, the assigner (or creator), earlier commenters and colleagues mentioned earlier who can open the task.
- **A mention in a task comment is a third read path to the task (D-20).** Typing `@` in the comment box offers every user who may sign in and holds `task.view_any` (through a role or a direct grant), except the author — deliberately not limited to the author's assignment reach, so an `employee` can pull in a manager or a colleague from another team (`TaskService::mentionableUsers`); other ids sent to the server are dropped. The mention is stored per comment (`task_update_mentions`) and makes the colleague a **participant**: `TaskPolicy::view` asks, in order, `task.view_any`, the own/team/all scope (`RecordVisibilityResolver::canRead`), participation (`App\Services\Tasks\TaskParticipants`, one memoised query per user and request) and the linked-record path; `TaskResource::constrainToReadable()` adds the same participant subquery at the own and team levels (at `all` nothing needs adding; without `task.view_any` neither path opens). So a participant opens the task, reads the whole thread, downloads its files (with `attachment.download`) and comments, and the task appears wherever the task list query reaches — the task list and its tabs and badges, global search, the calendar (read-only) and exports within scope. Participation grants **nothing else**: `update`, `progress` (start, post update, complete, reopen), `cancel`, `delete`, `restore` and assignment keep their own rules, so the edit page, the calendar move and edit, and every status action stay refused. Uploading follows `AttachmentPolicy::create`, which asks for the task's `view`: a participant holding `attachment.create` may add files to the task (as any reader of a task may, D-15). A mention cannot be withdrawn — like the comment that holds it, it is append-only — so the access lasts as long as the task; taking `task.view_any` away, or disabling the account, closes it. The mentioned colleague is told with `TaskMentionNotification` (`NotificationEvent::TaskMention`, bell and mail on by default, offered with `task.view_any`) instead of the general comment notice, and hears about later comments like every participant.
- **Routine tasks belong to the people who hand out work (D-22).** *Tasks → Routine tasks* in the Tasks workspace (`TaskTemplateResource`, `TaskTemplatePolicy`) is gated by `task.assign` alone — no new permission key: viewing, creating, editing, pausing, resuming and deleting a routine, single and bulk, all need it; `restore` and `forceDelete` are refused (a routine is configuration, not soft-deleted: deleting it removes it and keeps the tasks it already created). The policy has no record scope: every `task.assign` holder reaches every routine. The assignees, however, are checked on every save against the saver's assignment reach (`RecordVisibilityResolver::assignableUsers`: active users holding `task.view_any`), exactly as when a task is created for someone — so a custom role granted `task.assign` at team level can only put its own team on a routine. **Whoever last saved a routine is its assigner**: its tasks are handed out in that person's name (D-14: the assignee reports progress, completion notifies the assigner), and a save by someone other than the stored assigner is written to the ledger as a takeover even when nothing else changed. On each scheduled day the hourly `tasks:generate-routines` skips an assignee who may no longer sign in or no longer holds `task.view_any`.
- The task performance report's average time to finish (D-21) adds no permission: *Reports → Tasks* stays behind `reports.view`, one line per assignee within the reader's task scope (`ReportFilters::scope` through `RecordVisibilityResolver`), and its export follows the same rule.
- `roles.manage` is more than role administration: it opens **System → Backups** and the authorised route `backups.download` (a full database dump and the private files, D-16), makes its holder a recipient of `BackupFailedNotification`, and adds the system-health part to their weekly summary (D-18). Grant it to a custom role only for someone who may take a copy of the whole database.
- `task.assign` also decides who receives the weekly summary (D-18, `crm:weekly-summary`, Thursday 22:30): every active holder, through a role or a direct grant, gets the organisation's task week (titles and assignees organisation-wide, links only where their own `view` allows). Granting it to a custom role therefore adds that mail as well as the assign verb.
- The notification preferences page offers an event only to holders of the permission its notices depend on (D-19): record assignment, any `{entity}.view_any`; task events (a mention in a task comment included, D-20), `task.view_any`; deal events, `deal.view_any`; lead events, `lead.view_any`; note mentions, `note.create`; weekly summary, `task.assign`; backup failed, `roles.manage`. Taking a permission away hides the choice but keeps the stored preference, which applies again when the permission comes back.
- Soft-deleted records are frozen: every write verb refuses a trashed record; restore is the only action left.
- Seeded roles keep their machine key; `super_admin` cannot be edited at all.
- Permanent deletion is never granted (`forceDelete` = false everywhere, D-13).
- The audit ledger is append-only (`ActivityLogAppendOnlyObserver`) and readable only with `audit.view`.

## Adding a permission

1. Add the case to `App\Enums\Permission` (`{group}.{verb}`), and the verb/group labels to `lang/{ar,en}/permissions.php`.
2. Grant it in `RolePermissionMatrix` for the roles that should hold it by default.
3. Check it in the policy (`$this->verb($user, 'verb', $record)` for owned entities).
4. Run `php artisan db:seed` — existing editable roles keep their current sets; super admins grant the new key from the Roles screen.

`Tests\Feature\Access\RoleSeedingTest` and `PermissionMatrixTest` fail if the catalogue, the seeder and the matrix disagree.
